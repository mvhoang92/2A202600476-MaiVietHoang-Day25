## 1. Architecture Summary

The system is a production-style reliability gateway that sits between the user and two
`FakeLLMProvider` instances. Every request flows through four layers in order:

```
User Request
     │
     ▼
┌─────────────────────────────────────────────────────────┐
│                   ReliabilityGateway                    │
│                                                         │
│  1. Cache check ──────────────────────────────────────► HIT → return cached
│       │ MISS                                            │     route: "cache_hit:{score}"
│       ▼                                                 │
│  2. CircuitBreaker: primary ──────────────────────────► FakeLLMProvider "primary"
│       │ OPEN → fail fast                                │     fail_rate=0.25, ~180 ms
│       ▼                                                 │
│  3. CircuitBreaker: backup ───────────────────────────► FakeLLMProvider "backup"
│       │ OPEN → fail fast                                │     fail_rate=0.05, ~260 ms
│       ▼                                                 │
│  4. Static fallback message                             │
│       "The service is temporarily degraded."            │
└─────────────────────────────────────────────────────────┘
```

**Route reasons emitted (specific, not generic):**

| Route label | Meaning |
|---|---|
| `primary:primary` | Served by the primary provider |
| `fallback:backup` | Primary circuit open; served by backup |
| `cache_hit:1.00` | Exact cache hit |
| `cache_hit:0.94` | Similarity cache hit (score shown) |
| `static_fallback` | All providers failed |

**Key design decisions:**
- Cache is checked before any provider call — a hit costs 0 ms and $0.
- Circuit breakers are per-provider; they fail fast with `CircuitOpenError` when OPEN.
- On success, the response is written to cache so future identical/similar queries are free.
- `SharedRedisCache` uses the same interface as `ResponseCache` — the gateway is backend-agnostic.

## 3. Circuit Breaker Implementation

The state machine in `circuit_breaker.py` implements the full 3-state cycle:

```
         failure_count >= threshold
CLOSED ──────────────────────────────► OPEN
  ▲                                      │
  │  probe_success                       │ reset_timeout_elapsed
  │  (success_count >= success_threshold)│
  └──────────── HALF_OPEN ◄──────────────┘
                    │
                    │ failure in HALF_OPEN
                    └──────────────────────► OPEN (re-opens immediately)
```

**No retry storm:** when the circuit is OPEN, `allow_request()` returns `False` immediately
and `CircuitOpenError` is raised — the provider is never called. The gateway catches this
and moves to the next provider in the fallback chain.

**Transition log sample** (from `primary_timeout_100` scenario, primary fail_rate=1.0):

```
[primary] closed    → open       reason=failure_threshold
[primary] open      → half_open  reason=reset_timeout_elapsed
[primary] half_open → open       reason=failure_threshold   ← probe failed, re-opens
[primary] open      → half_open  reason=reset_timeout_elapsed
[primary] half_open → open       reason=failure_threshold
[primary] open      → half_open  reason=reset_timeout_elapsed
[primary] half_open → open       reason=failure_threshold
```

The primary never recovers (fail_rate=1.0), so it oscillates OPEN↔HALF_OPEN throughout
the simulation. All traffic is served by the backup provider.

## 5. In-Memory Cache & Cost Analysis

### Similarity function

The baseline used plain token Jaccard overlap. The improved `ResponseCache.similarity()`
uses a **weighted combination of character trigrams + token Jaccard**:

```python
score = 0.6 * trigram_jaccard(a, b) + 0.4 * token_jaccard(a, b)
```

Trigrams are more robust than token overlap for paraphrases and minor wording changes.
An exact-match fast path returns 1.0 immediately without computing trigrams.

### False-hit guardrails

Two layers of protection:

1. **Privacy guardrail** (`_is_uncacheable`): queries matching patterns like
   `balance`, `user \d+`, `account \d+`, `ssn`, `password`, `credit card` are never
   cached and never served from cache.

2. **Year/ID guardrail** (`_looks_like_false_hit`): if the query and the cached key
   contain different 4-digit numbers, the match is rejected even if similarity ≥ threshold.

**False-hit example caught:**

```
query:        "Summarize refund policy for 2026 deadline"
cached_query: "Summarize refund policy for 2024 deadline"
similarity:   0.8039  (below threshold 0.92 → rejected by threshold)
guardrail:    _looks_like_false_hit → True  (2026 ≠ 2024 → also rejected by guardrail)
result:       None  ✅ correct — stale 2024 policy not served for 2026 query
```

**Privacy example:**

```
query:  "Give me the current account balance for user 123"
result: None  ✅ correct — privacy guardrail blocks caching and lookup
```

### Cache comparison (seed=42, 100 requests, all-healthy providers, 4 unique queries)

| Metric | Without cache | With cache | Delta |
|---|---:|---:|---|
| latency_p50_ms | 205.33 | 0.04 | −99.98% |
| latency_p95_ms | 237.50 | 0.16 | −99.93% |
| estimated_cost | $0.062350 | $0.002330 | −96.3% |
| cache_hit_rate | 0.00 | 0.96 | +0.96 |

With 4 unique queries repeated 100 times, the cache absorbs 96% of requests after the
first round, reducing cost by 96% and median latency by ~5 000×.

**Threshold justification:**
- `0.85` → false hit: "refund policy for 2024" matched "refund policy for 2026"
  (combined score ≈ 0.86 > 0.85).
- `0.92` → no false hit: combined score ≈ 0.80 < 0.92, correctly rejected.
- The `_looks_like_false_hit` guardrail provides a second independent layer.

**TTL justification:**
- `300 s` (5 min): FAQ and policy queries are stable within a session. A shorter TTL
  (e.g., 60 s) would reduce hit rate significantly; a longer TTL (e.g., 3600 s) risks
  serving stale policy text after an update. 5 min is a reasonable balance.

## 6. Redis Shared Cache

### Why in-memory cache is insufficient for production

In-memory cache is **per-process**. With three gateway pods running on separate machines:

- Pod-1 answers "What is a circuit breaker?" and caches it locally.
- Pod-2 receives the same query — its cache is empty, so it calls the provider again.
- Cache hit rate scales as `1/N_pods` instead of approaching 1.0.

`SharedRedisCache` stores all entries in a single Redis instance. Any pod that answers
a query writes to Redis; any other pod that receives the same (or similar) query reads
the cached answer. Hit rate is consistent regardless of which pod handles the request.

### Implementation

```python
# set(): hash the query, store as Redis Hash, set TTL
key = f"{self.prefix}{self._query_hash(query)}"
self._redis.hset(key, mapping={"query": query, "response": value})
self._redis.expire(key, self.ttl_seconds)

# get(): exact-match first, then similarity scan
exact_key = f"{self.prefix}{self._query_hash(query)}"
response = self._redis.hget(exact_key, "response")
if response:
    return response, 1.0
# ... similarity scan over all prefix keys
```

Both `_is_uncacheable` and `_looks_like_false_hit` guardrails are applied in Redis
`get()` — same protection as in-memory cache.

**Graceful degradation:** all Redis operations are wrapped in `try/except`. If Redis is
unreachable, `get()` returns `(None, 0.0)` (cache miss) and `set()` silently skips
storage. The gateway continues serving requests via providers.

### Evidence of shared state

Two separate `SharedRedisCache` instances pointing at the same Redis URL share data:

```python
c1 = SharedRedisCache("redis://localhost:6379/0", 300, 0.5, prefix="rl:demo:")
c2 = SharedRedisCache("redis://localhost:6379/0", 300, 0.5, prefix="rl:demo:")

c1.set("circuit breaker explanation",
       "A circuit breaker has 3 states: CLOSED, OPEN, HALF_OPEN.")
val, score = c2.get("circuit breaker explanation")
# Output:
# c1.set -> c2.get: "A circuit breaker has 3 states: CLOSED, OPEN, HALF_OPEN." score=1.0
```

This is verified by `test_shared_state_across_instances` in `tests/test_redis_cache.py` ✅

## 10. Failure Analysis

**Remaining weakness: circuit state is per-process, not shared across instances.**

If three gateway pods run simultaneously, each has its own `CircuitBreaker` object in
memory. Pod-1 may have its circuit OPEN (having seen 3 failures) while Pod-2 still has
it CLOSED and keeps sending requests to the failing provider. This means:

- The failing provider receives up to `N_pods × failure_threshold` requests before all
  pods open their circuits.
- Recovery probes are uncoordinated — all pods probe simultaneously at their own
  `reset_timeout`, potentially overwhelming a recovering provider with a burst of traffic.
- There is no global view of circuit state; monitoring dashboards would show inconsistent
  states across pods.

**Proposed fix:** Store circuit breaker counters in Redis using atomic `INCR` and `EXPIRE`
commands. A shared `failure_count:{provider}` key means any pod's failure increments the
global counter, and the circuit opens cluster-wide after `failure_threshold` total
failures. State transitions would use Redis `SET`/`GET` with optimistic locking (WATCH +
MULTI/EXEC) to prevent race conditions.

   report from a passive measurement into an active reliability gate in CI/CD.
